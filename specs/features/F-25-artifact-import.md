# Feature: Artifact import

**ID:** F-25
**Category:** artifacts
**Milestone:** M0 (already in v0)
**Status:** Proposed
**Parent epic:** sv-4wh9

## Summary

Artifact import consumes files/directories produced by an upstream step.
GitHub uses `actions/download-artifact`; GitLab uses `needs` (implicit
artifact passing). Sverka models this as `importArtifact` operations
generated by synthesis when a `StepRef` with type `artifact` appears in a
step's inputs.

## Provider matrix

| Aspect | GitHub Actions | GitLab CI | Sverka (proposed) |
|--------|---------------|-----------|-------------------|
| Construct | `actions/download-artifact@v4` | `needs` (implicit) | `importArtifact` operation (auto-generated) |
| Semantics | action downloads named artifact to a path | artifacts from needed jobs are available automatically | engine copies from ArtifactStore to step workspace |
| Value type | action `with` (name, path) | n/a (implicit) | name, from (producer), output |
| Limitations | must know artifact name | must declare `needs` | auto-generated from StepRef inputs |
| Provider gap | — | — | — |

## GitHub Actions

```yaml
deploy:
  needs: [build]
  steps:
    - uses: actions/download-artifact@v4
      with:
        name: build-dist
        path: dist/
    - run: ls dist/
```

`actions/download-artifact@v4` downloads a named artifact to a local path.
The job must declare `needs` on the producing job.

## GitLab CI

```yaml
deploy:
  needs: [build]
  script: [ls dist/]
```

When `needs` is declared, artifacts from the needed job are automatically
available in the working directory. No explicit download step required.

## Sverka proposal

### Portable model

`importArtifact` operation (`core/graph.ts:67-72`):

```ts
{ kind: "importArtifact", name: string, from: string, output: string }
```

- `name`: local destination path in the step workspace (preserved across all
  providers — the artifact is placed at this path regardless of the producer's
  output name)
- `from`: producer step ID
- `output`: output name on the producer

Generated by synthesis (`core/synthesize.ts:148-178`) when a `StepRef` with
`type: "artifact"` is in `step.inputs`. Also creates an `artifact` dependency
on the producer.

### Authoring API

Artifact imports are implicit — they are generated when a `StepRef` with
type `artifact` is used in a step's inputs:

```ts
// SDK — StepRef with type "artifact" auto-generates importArtifact
const distRef: StepRef = { kind: "step", step: "build", output: "dist", type: "artifact" };
sh`ls ${distRef}`.build(pipeline, "deploy");
// → synthesis generates: { kind: "importArtifact", name: "dist", from: "ci/build", output: "dist" }

// Construct — explicit inputs
new ShellStep(pipeline, "deploy", {
  command: "ls dist/",
  inputs: [{ kind: "step", step: "build", output: "dist", type: "artifact" }],
});

// Decorator
@step({ inputs: [stepRef("build", "dist", "artifact")] })
```

### Lowering

- **GitHub target:** `importArtifact` → `actions/download-artifact@v4` step
  with `name: <fromShortId>-<output>`, `path: <name>` (the `name` field is
  used as the destination path, preserving the import destination across
  providers)
  (`github/lower.ts:396-404`). Preceding `run:` steps are flushed first.
- **GitLab target:** `importArtifact` → adds `needs: [producerJob]`
  (`gitlab/lower.ts:505-509`). No explicit download — GitLab passes artifacts
  implicitly via `needs`. Artifacts appear at the producer's output path; if
  this differs from `name`, a staging/rename step is emitted.
- **Native engine:** `StepExecutor.executeImportArtifactOperation`
  (`engine-native/step-executor.ts:167-178`) calls
  `ArtifactStore.retrieve(producerId, output, destPath)`. The artifact is
  copied from the producer's directory in the artifact store to the step
  workspace.

### Capability manifest

```ts
"operation.import": "lowered",  // GitHub: download-artifact; GitLab: needs
```

### Portability & divergence

GitHub requires an explicit download action; GitLab passes artifacts
implicitly via `needs`. Sverka handles both correctly: GitHub lowering emits
the download step; GitLab lowering just adds the `needs` edge (the artifact
appears automatically).

The `from` field stores the full producer step ID (e.g. `ci/build`); the
lowering shortens it to the job ID for artifact naming.

## Non-goals

- Artifact import from external pipelines (F-31, M2).
- Selective artifact import (importing specific files from an artifact).

## Dependencies

- **Depends on:** F-24 (artifact outputs — produces the artifacts to import),
  F-07 (DAG deps — import creates an artifact dependency).
- **Blocks:** none.

## Open questions

- Should `importArtifact` support renaming (import `output` as a different
  local name)? Currently `name === output`.
- Should the GitLab lowering emit `dependencies` explicitly for clarity?
